Real-Time Auction System

Scaling a Go WebSocket server to 10,000+ bids per minute

GitHub ↗
>10K Bids / Min
<1ms Propagation Latency
Auto Scales via K8s HPA

The Challenge

A real-time bidding engine demands ultra-low latency and strict concurrency safety. A single dropped or duplicated bid in the final seconds of an auction breaks trust permanently.

Architecture

  • Go & WebSockets: Persistent connections for instantaneous, sub-millisecond bid propagation to all active clients.
  • Redis Pub/Sub: Decoupled architecture enables seamless horizontal scaling — new worker nodes join the broadcast mesh automatically.
  • Optimistic Locking: PostgreSQL row-level versioning combined with Redis sorted sets eliminate race conditions and duplicate bids during high-concurrency spikes.

Event-Driven · Data Pipeline

JobMeld Automation Pipeline

Fault-tolerant job scraping with exactly-once Kafka processing

GitHub ↗
60% Manual Effort Saved
0 Duplicate Records
2+ Data Sources

The Challenge

Scraping unstructured job postings from multiple sources at volume creates high failure rates and data duplication — both of which silently corrupt downstream state.

Architecture

  • Apache Kafka + Zookeeper: Raw scraped HTML streams into a centralized processing queue, fully decoupling scrapers from parsers and enabling independent scaling.
  • Exactly-Once Processing: Kafka consumer offsets are committed atomically within PostgreSQL transactions; Redis caches deduplicate job IDs on ingestion before any I/O hits the database.

Building a robust document Q&A system requires efficient chunking, high-dimensional vector search, and a backend resilient enough to handle live demo traffic without failing.

Architecture
